# Taste
- Prefers to start a new feature with a minimal, self-contained proof-of-concept (e.g. a simple standalone HTML page) to validate the approach before building the full integration. Confidence: 0.65
- Prefers fully client-side / serverless solutions: work should run in the browser with no servers or backend. Confidence: 0.7
- Expects new integrations to honor the framework's existing conventions and contracts rather than merely work in isolation — e.g. a new language runtime must support the same interop surface as existing ones (stdin, stdout, stderr, compiler diagnostics, exit code), and when asked to build something "similar to" a named sibling package, wants that existing package studied first so its structure, API shape and helpers are mirrored. Confidence: 0.6
- Insists that public-facing names and labels accurately describe what a feature actually is; would rather replace or remove a misleading offering than keep it for compatibility, especially when it risks confusing users. Confidence: 0.6
- Wants an online playground/sandbox to closely mirror the real local development environment — i.e. emulate how developers actually work in practice (the common `dune build && dune exec` + stdin/stdout/exit-code loop) rather than adding capabilities that only serve a narrow, uncommon workflow; explicitly restates this as the yardstick ("I want this to be similar to local dev as much as possible"), so fidelity to the real local workflow outranks convenience shortcuts. Confidence: 0.8
- When weighing a new technology or implementation against an existing one, wants an explicit advantages/disadvantages comparison (grounded in the actual existing code) before a recommendation, not a bare verdict; likewise, when pursuing parity with a reference environment — or before entering the next phase of work (e.g. "what is missing now to be ready to start X integration?") — expects a "what is missing?" gap analysis: gaps ranked worst-first, the single true blocker named explicitly, next steps prioritized by value per unit of effort, work that can proceed in parallel identified, and unverified areas called out as unverified rather than guessed. Confidence: 0.7
- Prefers resources/capabilities to be lazy-loaded on demand rather than bundled or linked in eagerly — unused features should cost nothing until actually used. Confidence: 0.6
- Wants setup to be auto-discovered with no per-item manual configuration or pre-building (e.g. discovery from the switch/environment, drop-in directories) — favors zero-config workflows over explicit per-entity registration. Confidence: 0.6
- Prefers new runtime/bundle components to integrate into the host's existing infrastructure and leave the host in control — e.g. expose a plain callable API like `self.ocamlWasm.run()` that never hijacks `onmessage`, so a host that already owns a worker keeps its own protocol, rather than shipping a nested/duplicate worker. Confidence: 0.7
- Prefers avoiding environment lock-in and wants components to be portable where feasible — questions a "browser-only" implementation and asks whether a structural change can make it usable in Node/others too. Confidence: 0.6
- Prefers avoiding unnecessarily duplicated heavy resources (e.g. not paying a second 4.2 MB worker parse when the runtime can be imported into an existing worker via `importScripts`). Confidence: 0.55
- Wants failures to surface explicitly to the caller instead of being thrown-and-lost or silently swallowed (e.g. a `run` call that never hangs or throws but returns an `error` field, with the same message mirrored into diagnostics so a null exit code still carries an explanation) — "nothing happened" must never be indistinguishable from a hang or a crash. Confidence: 0.6
- Wants a library/runtime component to be told its configuration explicitly via an option at creation time (e.g. `baseUrl` passed to `createCompiler`) rather than inferring it implicitly from the environment, especially when implicit inference only works by accident. Confidence: 0.55
- When a failure follows an earlier structural change, wants the causal link examined explicitly (e.g. asking whether removing the synchronous XHR reader is actually related to the failing `importScripts` path) rather than treating correlation as causation or piling on more fixes. Confidence: 0.5
- Expects the agent to keep iterating until the thing actually works rather than stopping to report partial progress or an honest-but-incomplete status when blockers remain; treats a run-out-of-budget summary as premature and pushes to continue rather than replying with a new request. Uses bare "continue" to mean "proceed without further check-ins", and states the bar explicitly when pressed ("keep re-iterating till you get it ready for usage", "do not stop till we are ready to use it in LiveCodes"). Confidence: 0.8
- Wants build artifacts committed to version control rather than ignored — deliberately comments out `.gitignore` entries so generated output is tracked; treats an agent re-adding gitignore rules for artifacts as an unwanted override. Confidence: 0.75
- Expects the agent to work until the change is verified working in the real target environment (e.g. actually running in the browser), not merely plausibly working based on an equivalent code path or a passing proxy harness. Confidence: 0.65
- Prefers additive, non-breaking migrations over in-place replacement: add the new implementation alongside the existing one, deprecate the old explicitly first, and swap them later — so existing references (e.g. a language id in `l=...` share links) keep resolving and nothing breaks during the transition. Confidence: 0.65
- When adding something to an existing project, asks for a recommended name rather than inventing one, and expects it to follow the project's established convention for equivalent items (e.g. a sibling variant's `<base>-wasm` / `Display (Wasm)` language id, or a package named after the language/toolchain it implements rather than the implementation variant). Confidence: 0.5
- For a language integration, expects the architecture the host framework already uses for equivalent features rather than a bespoke one: LiveCodes languages compile to JavaScript that the result page executes (as TypeScript, CoffeeScript, ReScript and Go do), so a new language must emit JS too — not run its own runtime in an iframe/worker. Will flatly correct an agent that proposes a different execution model and cite the existing implementations as the precedent. Confidence: 0.6
- Prioritizes making the current deliverable actually usable and integrated over continuing to broaden scope; deliberately pauses feature work ("I think I will stop adding features to that extent for now") to focus on finishing what exists, and reads continued investigation as servicing that goal. Confidence: 0.55
- Values thorough, self-contained project documentation for handover: wants a technical findings document capturing all the details — how to build and upgrade, what works versus what does not (with each claim marked verified/unverified), the approaches ruled out — plus a separate handover document detailed enough that a fresh session can pick up and continue. Confidence: 0.6
- Treats those handover/findings documents as living documents to be updated continuously as work progresses, not one-time artifacts — explicitly asks to "keep updating FINDINGS and HANDOVER" alongside doing the work. Confidence: 0.6
- Wants strictly sequenced phases: prefers to finish and stabilize the upstream component before starting the dependent integration work, and will explicitly forbid beginning the downstream phase early ("do not start LiveCodes integration till ocaml side is ready"). Confidence: 0.55
 Holds a strict definition of done for releases: will not publish a package or begin the downstream integration until everything is finished, explicitly including non-blocking/optional items — a known-but-deferred gap is still reason to hold the release rather than ship and follow up later. Confidence: 0.7
